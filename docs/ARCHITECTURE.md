# K&K redesign — architecture & contracts (binding for every engineer)

Java 11 source level (`--release 11`): **records, switch expressions and text blocks are not allowed**. libGDX 1.14.1, ShapeDrawer 2.5 API (`space.earlygrey.shapedrawer.ShapeDrawer`; the build pins 2.5.0), Jackson 2.17 **streaming core only** (`jackson-core`; jackson-databind is not used: its bean introspection calls `Method/Constructor.getParameterCount()`, API 26, see §7), FreeType. Android minSdk 21 (Java 8 APIs via desugaring are OK: `java.util.function`, streams OK but avoid in render loops).

**Wave 2 (owner decisions of 2026-10-12, as built):** folded into §5, §10, §13, §18–§20 and indexed in §21; superseded text is marked **Replaced**.

Visual / UX decisions live in `docs/DESIGN.md`. This file defines **code structure, ownership and APIs**. When DESIGN.md and this file disagree about code structure, this file wins; for looks, DESIGN.md wins.

## 0. Golden rules
1. **No per-frame allocation** in render/update/input paths (no `new` of GlyphLayout/Color/Vector2/String.format/lambdas/iterators over ArrayList in hot loops — use indexed loops, reuse fields, `StringBuilder` + cached digits).
2. **No StretchViewport anywhere.** World = `ExtendViewport(1920, 1080)` (min world 1920×1080, longer axis extends). Camera centred at (960, 540) for gameplay; menus may anchor to visible edges via `Ui`.
3. **GL objects are never static** (Android context loss). They belong to `Main`'s services or to a screen, created once, disposed in `dispose()`.
4. Screens are **created once and cached** by `Main` (except throwaway ones), `show()` must be idempotent (no re-allocation), `hide()` releases input/music only.
5. Screen switches go **only** through `Main.transitionTo(...)` / `Main.switchNow(...)` which defer the actual `setScreen` to the start of the next frame (never inside another screen's render).
6. Fonts are baked **white** and tinted at draw time; never mutate a shared font's color without restoring it — use `Fonts.draw(...)` helpers.
7. Every user-visible string that can contain non-ASCII (player names, song titles) is drawn through `Fonts` which routes to the CJK font automatically.
8. Touch targets ≥ 48 dp (`Ui.dp(48)` in world units). Act on **release (tap)**, never on touchDown, except gameplay note input.
9. Android BACK (`Gdx.input.setCatchKey(Input.Keys.BACK, true)` set once in Main) and desktop ESC map to each screen's "back" action via `Main`'s global key handling → `KkScreen.onBack()`.
10. Keep code idiomatic to the existing style (4-space indent, Javadoc on public classes). Remove dead editor leftovers you touch. No `Gdx.app.log` in hot paths.

**As built (integration, binding; the code wins per §14):** `Slot { MENU, PREVIEW, RESULT, HIT }`; MENU is `assets/background.(ogg|mp3|wav)`. `hitSound()` loads and primes (one volume-0 play) all four reserved Sound slots together on first use: `Sounds/hit.*`, `hit_echo.*` (ECHO instead of `hit`), `hold_end.*` (`playHoldEnd()`) and `mine.*` (`playMine()`, called on a touched mine; a mine never plays `hit`), each `<name>.wav` then `<name>.ogg`, volume `sfxVolume`, silent when absent. With a platform `HitOutput` (`setHitOutput`, Android 8.0+), the `.wav` slots are also loaded into it as PCM and play there instead: `playHit(j, atNanos)` is heard at that instant (`GameplayScreen` passes a judged touch's event time, and queues autoplay's hits ahead at their notes), `cancelTimedHits()` on pause (DESIGN §5.14). `playResult(song)`: the song folder's `result.(ogg|mp3|wav)` started at the manifest's `resultMusicStartMs` (the offset applies only to that per-song file), else `assets/Audio/result.(ogg|mp3|wav)`, else the temporary `assets/Introduction/Introduction.wav`, else silence; fades in over `RESULT_FADE_IN` 1.2 s to `musicVolume × RESULT_GAIN` (0.8) and loops. Owner-facing slot docs: `assets/Audio/README.txt`, `assets/Sounds/README.txt`, `docs/ASSET_SLOTS.md`.
`SongClock` (gameplay clock; one instance owned by GameEngine):
```java
void load(FileHandle music);            // creates Music, reads duration (WavDurationUtil for .wav else from metadata/fallback)
void prepare(float startMs);            // lead-in start (negative ms allowed), paused
void start(); void pause(); void resume(); void seek(float ms); void dispose();
boolean startCountIn(float ms);        // the resume countdown runs the music in, muted, from ms back (Android)
double countInMs(); double countInLeftMs(); // the count-in's song time; how long until the frozen time
void update();                          // once per frame BEFORE input is used? (see below)
double nowMs();                          // smoothed song time at "now" (System.nanoTime()), audio-anchored
double timeAtNanos(long nanos);          // song time at an input event timestamp (Gdx.input.getCurrentEventTime())
long nanoTime();                         // the clock's time-source reading (System.nanoTime unless a test replaced it)
void setTimeSource(SongClock.TimeSource s); // tests only
void attach(Music m, float durationMs, boolean takeOwnership); // attach(null, …) = a silent run (no music)
float durationMs();
```
Behaviour: during lead-in (t<0) time runs from nanoTime; when t crosses 0 the music starts. **With music attached, that crossing anchors song time 0** at the frame the stream starts at position 0, so audio and clock agree from the first frame (`nowMs()` was < 0 the frame before, so time never goes back); a **silent run** (`attach(null, …)`) keeps the exact nanoTime timeline. While playing, `t = anchorSongMs + (nanoNow - anchorNanos)/1e6` and every frame the anchor is nudged toward `music.getPosition()*1000` (only when the reported position changed, and only while `music.isPlaying()`) with gain 0.1 and a hard resync if drift > 60 ms; **audio is never seeked during play**. Paused → time frozen. Resumed → the clock stays at the frozen time until the reported position moves (at most `MAX_START_LEAD_MS` = 400 ms), then takes that position; **on Android the song is first seeked to the frozen time** (`setReseekOnResume`, tests only): MediaPlayer's own clock runs on from a plain resume while the sound comes back later and some devices never win that back, so each pause left the music later than the chart (2026-10-15). Looping music (calibration) and a resume past the end of the file are not seeked. **The music runs in through the countdown** (Kelvin 2026-10-21 15:09; it replaced the priming of 7.105 and the learned resume latency of 7.106): where a resume re-seeks (Android), `GameEngine.startCountIn(3000)` → `SongClock.startCountIn(ms)` plays the music muted from `ms` before the frozen time P (positioned its start lead ahead, so it sounds where the clock is) while `nowMs()` and `timeAtNanos()` stay at P and `isRunning()` stays false; the clock runs along with that music (`countInMs()`, settled like a song start, hard resyncs allowed). `GameplayScreen` shows the 3 × 1 s digits from `countInLeftMs()` and calls `resume()` once it reaches 0, so the run goes on from P with the music already playing, now at full volume (`setVolume` and fades leave a count-in muted). A count that reaches back past the song start runs the lead-in again and starts the music from 0 as at a song start; past the end of the file, or when the player does not play, the count runs on time. `pause()` during the count freezes P again, pauses the music and restores its volume (the back key reopens the menu). Desktop (no re-seek), looping music and a pause in the lead-in return false and resume plainly. **After any resume the clock catches up by a slew** (13:13): an error up to `SETTLE_GROSS_MS` (250 ms) moves the anchor by at most `RESUME_SLEW` (10 %) of the time since the last position update, never by the 60 ms hard resync, until the clock is within 15 ms of the music; after a count-in there is normally nothing left to catch up. **On Android an MP3 whose Info header has a table of contents plays from `Mp3Info.seekableCopy`**: MediaPlayer seeks such a file by that table (100 entries of 1/256 of the file) and reports the requested time, which landed 0.1–1.2 s away on the owner's files; the copy (local `cache/music/<name>-<path hash>.mp3`, written once, reused while its bytes match) only clears the table's flag, so the extractor seeks the constant-bitrate stream by its bitrate, exactly, and still skips the Info frame and reads its LAME delay and padding. VBR ("Xing") files, other formats and desktop play the file itself.

**Offsets (binding, GAMEPLAY + SHELL agree; DESIGN §9.4/§9.5):**
* `judgeTime = clock.timeAtNanos(eventNanos) − audioOffsetMs`, where `audioOffsetMs` is the **active output's** offset from `device.json` (`profiles().device().audioOffsetMs()`, per output SPEAKER / WIRED / BT, clamped −300..300). Positive = the player hears audio late, so judge times shift later. Frame-based work (LOST sweep, holds, mines, autoplay) uses `clock.nowMs() − audioOffsetMs`.
* `visualTime = judgeTime + visualOffsetMs` (`device.json`, clamped −150..150). Notes, lines, lanes **and the hit-test geometry** (line y and lane spans used to resolve a touch) are evaluated at the visual time, i.e. where the player saw them. **A positive visual offset makes notes arrive earlier** (it compensates a display that shows frames late).
* `GameplayScreen` reads both values in `begin()` and again when the pause menu resumes (`GameEngine.setOffsets`), so a change applies on the next run or resume.
* Calibration APPLY stores `round(median(tap − beat))` (clamped −300..300) directly as the active output's audio offset, because calibration measures the raw clock with the same convention. The §9.5 visual test flashes at `nowMs − audioOffsetMs + visualOffsetMs`.

**Input timestamps.** `GameplayScreen` validates each event time against `clock.nanoTime()` (not `System.nanoTime()` directly): an event time ≤ 0, later than now or more than 1 s old falls back to now. A test that replaces the clock's time source with `setTimeSource(...)` must therefore also proxy `Gdx.input.getCurrentEventTime()` onto the same base, or every touch is judged at "now".

**Own song output (Android 8.0+, 2026-10-27).** `AudioService.setMusicOutput(MusicOutput)` (set by `Main` when the platform `HitOutput` is also a `MusicOutput`, i.e. `android/AndroidHitOutput`) and `SongClock.setMusicOutput` (set by `GameplayScreen` before `load`): `load` first asks the output to `open` the song. `android/SongDecoder` decodes it on a background thread (`MediaExtractor` + `MediaCodec` configured with the extractor's format, so an MP3's encoder delay and padding are trimmed as by the system player and `audioDelayMs` stays 0) into a `PcmBuffer`, converted to the output rate by `Resampler` (windowed sinc). `HitMixer` mixes the song with the hit sounds in the one low-latency `AudioTrack`; song frame `s` of the current segment sounds at stream frame `segStream + (s − segSong)`, a segment starts `SONG_START_MS` (100 ms) after `play()` (or at the first frame not yet written when the queue is longer), pause and seek end it with a `FADE_MS` (5 ms) fade, and `songHeard(nanos)` is the frame heard at that instant from the output's timestamps. `MixerMusic` puts this behind libGDX `Music`, so `SongClock` runs unchanged except: `lead()` is the known start delay, there is no start-latency measurement (`preroll = 2`) and no settle period at a song start or count-in. Autoplay hit sounds are queued on chart time (`clock − audioOffsetMs`). Logcat tag `KKSync` logs the output in use, each pause, count-in start, the clock − music error at the count end and 1 s after a resume. When `open` returns null (Android below 8.0, an undecodable file, no first audio within 2 s) or throws, the old libGDX `Music` path is used. Desktop, menu, preview, result and calibration music are unchanged.

## 10. Gameplay contract (GAMEPLAY)
* `GameplayScreen extends KkScreen`: `begin(Chart chart, SongMeta song, Difficulty diff, boolean autoplay)` resets everything without reallocating GL objects; finish → builds `PlayResult` → `game.showResult(result)`; Back/ESC/Android BACK/app pause → pause menu (Resume with 3-2-1, Retry, Quit to map). `IntroductionScreen extends GameplayScreen` (tutorial).
* Input: one tap judges **at most one note**: candidates = notes in the lane(s) under the finger, in the line zone(s) whose |touchY − currentLineY| ≤ JUDGE_ZONE_HALF (world units = ref units because of the uniform ExtendViewport), unjudged, with |dt| ≤ TIER2_MS; choose the earliest judgement time (tie → smallest |dt|; then lane note before TIDE, own lane before neighbour, the closer line; when the two lines coincide and everything else is equal, the **LOWER** line's note wins; a lane note judged this way takes the TIDE notes of its exact beat and line with it, §20 joint judging); neighbour-lane tolerance: if none in own lane and touchX is within 30 % of a lane width from a boundary, try that neighbour. Taps earlier than −TIER2_MS consume nothing. Late beyond +TIER2_MS → LOST by the per-frame sweep. Use event timestamps (`Gdx.input.getCurrentEventTime()`) → `SongClock.timeAtNanos`. Per-lane cursor indices (no O(N) scans).
* Holds: head judged like a tap; pointer (or key) tracked through `touchDragged`. A hold is counted once, at its end: LOST when broken (combo break, LOST instead of the head grade), otherwise the head grade at completion. **End rule (binding, as built):**
  * a **lift or key-up before `end − HOLD_RELEASE_GRACE_MS`** breaks the hold at once;
  * **leaving the zone or the lane** (±1 lane tolerance) breaks it once the finger has been away for **more than 100 ms** (`HOLD_LEAVE_MS`), unless it comes back first;
  * **neither breaks it at or after `end − HOLD_RELEASE_GRACE_MS`** (250 ms before the end since 2026-10-12 21:09, was 133.33): a lift there, or a slide-off that started there, completes the hold;
  * a finger that **left the zone or lane and is lifted before it comes back** counts as released **when it left**, so lifting and keeping the finger down are judged the same (a slide-off at `end − 260` ms is LOST either way; one at `end − 240` ms completes either way);
  * a pause never breaks a hold: a pointer or key lifted while paused detaches it, and any pointer on it (or that lane's key down) within 100 ms after the resume re-grabs it. Keyboard (desktop) keeps the existing key map (CapsLock,A,S,D,F,J,K,L,;,' = 0–9; Tab,Q,W,E,R,U,I,O,P,[ = 10–19; by lane id since v2, §13.2).
* **System gestures (Kelvin 2026-11-06: players reported dropped touches).** On Android 10+ a swipe in from the left or right edge is the system's Back, and phone makers add their own (three-finger screenshot, the game toolbox's edge swipe). When the system takes a gesture it cancels every finger on the screen and reports nothing more about them, not even their lifting; libGDX passes on one `touchCancelled` and forgets the rest. So:
  * gameplay keeps the screen from the system's gestures while it runs (`ui/EdgeGuard`, `Main.guardEdges`): on Android 10+ `AndroidLauncher` excludes the whole game view (`setSystemGestureExclusionRects`, set again on every layout; the system's 200 dp limit does not apply while the navigation bar is stickily hidden). `GameplayScreen` asks for it on show and gives it back on hide and while the pause menu is open (the back gesture resumes there). Phone makers' own gestures cannot be excluded; players turn them off in the system settings;
  * `KkScreen.onGestureCancel` (the platform's `touchCancelled`) calls off every pointer's press on every screen, not just the reported one;
  * in gameplay `GameEngine.gestureCancelled()` lets every finger go without judging anything, and every hold a finger held then (a STREAM, a TIDE STREAM) is held by the engine to its end (`OWNER_KEPT`; a lapse already longer than `HOLD_LEAVE_MS` still breaks it); holds of keys stay with their keys. Paused, the fingers count as lifted (their holds detach). One pointer called off by a transition lock is still a release (`touchCancelled`).
* **Pause input (as built 2026-10-12, owner decisions; looks in DESIGN §5.3 and §5.12).** `gameplay/PauseControl` (public, pure Java, no GL, no allocation) owns the top-right control's geometry (`layout()`: ring r 32·k at x safe right + 24 − 26k − r, y halfway between safe top + 24 and the default sky line (never with the ring's outer edge within `TOP_CLEAR` 10 of that top edge; 2026-10-20 05:25), k = uiScale clamped .9–1.3; box ≥ `Ui.touchTarget()` × max(1, k) per side, extended to the screen edges) and its three modes, `Settings.pauseMode` = `PAUSE_DOUBLE_TAP` (1, default), `PAUSE_HOLD` (0, 0.35 s) or `PAUSE_SINGLE_TAP` (2). `GameplayScreen` gives the engine every touch first, then the control: `PauseControl.judges(engine, result, y)` is true (the down does not count and does not cancel a pending first tap) for `INPUT_JUDGED`, `INPUT_REGRAB`, a down that covers a running TIDE STREAM of its line, and a down for which `GameEngine.lastInputMine()` is true (it touched a MINE or made a LANE MINE contact). Double tap: a counted down within `DOUBLE_TAP_NS` (300 ms, event timestamps) of the first pauses. `pausesAtOnce(keycode)` = BACK, ESCAPE and the Pause key (P is an upper-row lane key, never a pause key). While paused, BACK / Esc / Pause / Enter resume. The pause menu is `gameplay/PauseMenu` (variant B: RETRY / RESUME / QUIT). `GameplayScreen.pausedBy` records "tap", "key" or "app" for the tests.
* Finish at `lastNoteEndMs + FINISH_DELAY_MS` (fade music), not WAV end.
* Rendering: uniform ExtendViewport, notes/lines/HUD per DESIGN §5, HitFx for effects, `game.audio().playHit(j)` at judgement time (no-op until a hit sound exists).

## 13. Lanes and note types — chart model v2 (owner change 2026-10-11, binding; overrides §8 lane rules and the 20-lane parts of §10)
The owner asked for: unlimited lanes; default lanes −4..−1, 1..4 (no lane 0); the existing window/bound ("缩进") logic unchanged; per-lane width and opacity that the future chart editor animates with the same power-function events as notes; two new note types (mine, universal tap). GAMEPLAY owns all of this (`elements/**`, ChartMapper behaviour) and implements it **first**, before the engine, with unit tests.

### 13.1 Lanes
* A lane is identified by a **non-zero int id**, unlimited in both directions. Negative ids sit left of positive ids; lanes are laid out in ascending id order (…, −2, −1, 1, 2, …). Lane 0 is invalid (rejected at load, logged once) unless it is an inserted lane (below).
* Both judgement lines share **one** lane set (as today: sky lanes 10–19 always had the same x as 0–9). Each note says which line it belongs to.
* Each lane has two animated channels, evaluated with the existing `Events.calculateValue(list, beat, base)` (power-function easing `initial + (final − initial)·p^exponent`, times in beats):
  * `width` (base 240): a **relative weight**, ≥ 0 (negative values clamp to 0).
  * `opacity` (base 1.0, clamped 0..1): multiplies the lane's own visuals only (lane ticks, separators (the old guides; a separator takes the brighter of its two lanes), column glow, approach glow, key hint). It does **not** change note opacity; notes keep their own `DisappearEvents`.
* **Lane modes (owner 2026-10-13, chart key `laneCount`, `Chart.laneLimit()`) and camera frame (owner 2026-10-13 05:28).** There is no window any more: lanes show across the screen (reference `LaneLayout.VIEW_LEFT` 0 .. `VIEW_RIGHT` 1920, stretched with `Field.x`). The **camera frame** `c(t)` (`LineEvents.cameraFrame` / `cameraFrameEvents`, type `CameraFrame`, `JudgementLine.cameraFrameAt`; reference units, positive = right, always absolute beats) moves the central axis, the border between lanes −1 and +1, to `x = 960 + c·kx` (`LaneLayout.axis()`).
  * **Unlimited (default: no `laneCount`; v1 always)**: every lane keeps its width in reference units, times the global lane scale `g(t)` (`LineEvents.laneScale` / `laneScaleEvents`, `JudgementLine.laneScaleAt`); lanes 1, 2, … follow each other rightwards from the axis, −1, −2, … leftwards. The screen only clips: a lane that reaches onto the screen keeps its whole span, also past the edge (never squeezed); a lane wholly off screen has zero width (not drawn, not touchable). The loader adds default lanes (`Lane.implicit()`, not written back) for id gaps and to cover the screen at the smallest scale and the farthest camera frame, up to ±64. The stretch (`Field.kx`) scales the tiles about the axis. Scaling some lanes only (owner's "partial scaling") is their own `widthEvents`.
  * **Finite (`laneCount` N)**: the declared lanes divide the frame `axis ± 960·g·kx` (the whole screen at scale 1, camera 0; not clipped) **in proportion to their widths**: with `W = Σ wᵢ`, `s = (right − left) / W`, lane i spans `x = left + s·Σ_{j<i} wⱼ` to `+ s·wᵢ`. If `W ≤ 0`, every lane has zero width at `left`.
  * Default v2 chart: 8 lanes × 240 = 1920, scale 1, camera 0 → 240 ref units per lane, full screen width (same look as before).
  * A charter widens one lane → in a finite chart the others narrow to keep the field inside the frame; to grow the field instead, animate the scale. A lane animated from width 0 → 240 "slides in".
  * **Old window keys** (`leftBound/rightBound`, `leftEvents/rightEvents`, `Events.TYPE.LeftBound/RightBound`) are only read, never written. v1: the window becomes scale `(right − left) / 2400` and camera `(left + right) / 2 − 960`; window events in left/right pairs (same start, end, exponent) become one `LaneScale` and one `CameraFrame` event each, unpaired ones are dropped (logged). So −240..2160 is scale 1, camera 0, and the shipped 0..1920 squeeze is scale 0.8. A finite v2 chart with a window and no `laneScale` / `cameraFrame` keys converts the same way with span 1920; an unlimited v2 chart's window is ignored (logged).
* **Inserted lanes (owner 2026-10-15, chart key `insert` on a lane, CHART_FORMAT_v4 §3.6).** 「轨道插入事件……在两条轨道之间插入一个新轨道，并自动压缩已在屏幕内显示的轨道……初始大小（默认为0，但可以突然出现），最终大小（默认为插入这条轨道后所有在窗口内的轨道的大小），增长速度（默认为1）……"插入0号轨"」. `Lane.insert()` is an absolute `Width` event (start, end, initial 0, final = the mean base width of the nearest non-inserted lanes by id, a missing one counting 240, exponent 1); `Lane.widthAt` is 0 before it, follows it while it runs and is the normal width channel after it (base width = final). Only an inserted lane may have id 0 (between −1 and 1); elsewhere the editor renumbers the outer lanes. **Unlimited:** `LaneLayout.tile` lays the lanes out from the axis as before (lane 0 centred on the axis; any other inserted lane shifts everything by half its width the other way, so both its sides move apart by half), then scales every span about the window centre `c` by `z = S / (S + I)` (`S` window width, `I` the inserted lanes' current screen widths; `squeeze()`), so the lanes at the window edges stay and the inserted lanes take their room from the screen; the axis, camera pans and the TIDE pattern width scale by `z` too. **Finite:** nothing extra (the weights share the frame). `ChartMapper.fillUnlimited` counts inserted lanes as 0 wide and reaches further by their widths. Keys: G / H (lower) and T / Y (upper) play lane 0 (`GameKeys` slots 20–23, Space = 24).
* **Deleted lanes (owner 2026-10-17, chart key `delete` on a lane, CHART_FORMAT_v4 §3.7).** 「加一个删除轨道事件，和插入轨道事件类似」. `Lane.deletion()` is an absolute `Width` event (start; end default = start; initial default = the lane's width at the start without it, so it does not jump; final default 0; exponent 1). The TIDE pattern factor `min(g, 1) × z` is capped at 1. **Finite:** nothing extra. Keys stay (no notes after a deletion; the editor flags them). `fillUnlimited` needs nothing extra (a deletion only shrinks what the screen needs).
* A lane whose screen width is < 1 ref unit is not drawn and not touchable.
* **TIDE pattern** (owner 2026-10-13 05:21): the T4 wave period and the pearl spacing are one "lane's worth" `LaneLayout.patternWidth()`, laid from `patternOrigin()`. Unlimited: `240 × kx × min(laneScaleAt(beat), 1)` from the axis (so it moves with the camera frame), at least screen width / `patternLanes()` (a per-chart bound from the smallest scale, ≤ `MAX_PATTERN_LANES` 128). Finite: frame / lane count from the frame left (as before).

### 13.2 Note types
JSON `type` strings are fixed (case-insensitive on read): `tap`, `hold`, `mine`, `universal`. Display names live in **one place**, `elements/NoteType` (`TAP, HOLD, MINE, UNIVERSAL`, each with `display`/`displayZh`), so a rename is one edit. Names (owner's choice 2026-10-11): TAP = DROP / 水滴, HOLD = STREAM / 水流, MINE = MINE / 水雷, UNIVERSAL = TIDE / 浪花.
* Every note: `line` (`"lower"` default, or `"upper"`), `judgement` (beats), `appearance`, `height`, `MovementEvents`, `RotationEvents`, `DisappearEvents` as today. `tap`/`hold`/`mine` need a valid `lane`; `universal` ignores `lane`. `hold` keeps `duration`.
* **tap / hold**: judged as in §10 (lane resolved through `LaneLayout.indexAtX`; neighbour-lane tolerance 30 % of the lane's *current* screen width).
* **universal** (tap only): judged by **any** tap whose y is inside that line's zone (`|y − lineY| ≤ JUDGE_ZONE_HALF`), at any x on screen. Keyboard: any key of that line's row (and Space for the lower line). Scored, combo'd and counted in `totalNotes` like a tap.
  * **Owner rule (2026-10-11): one tap takes the whole group.** All universal notes on the **same line** whose `judgement` value is **exactly equal** (same parsed float) form a group. The tap that judges one of them judges every unjudged member of the group at once, with the same Judgement and dt; each member still counts as its own note (`totalNotes`, score, combo += group size). Missed groups go LOST together. Universal notes on the other line at the same time are a separate group (they need a tap in that line's zone). Build the groups once at load (index of group start + size) so judging stays O(1).
* **mine**: never judged by taps and never consumes a tap.
  * It is **touched** only by a **press** (owner 2026-10-31, 「那个地雷我要求是点击才检查判没判定」): a `touchDown` whose judge time is within `[T − MINE_WINDOW_MS, T + MINE_WINDOW_MS]` (**±133.33 ms**, the ECHO window, since 2026-10-31; ±66.67 ms from 2026-10-13 21:55; ±100 ms on 2026-10-12–13) of the mine's time T and outside the cuts below, with `|y − lineY| ≤ JUDGE_ZONE_HALF` for the mine's line **and** `x` inside the central 70 % of the mine lane's current span (no neighbour tolerance), or a key-down of that lane's key in that time. A pointer or key already down, a drag into the box and a release never touch it, so a finger resting through a field of mines touches none of them.
  * Touched → `ScoreKeeper.mineTouched()`: combo → 0, `minesTouched++`, **no score or accuracy change**, no Judgement recorded. Each mine triggers at most once.
  * **MINEs and taps (owner 2026-10-31, 「如果和一个蓝键有判定区间重合，则水雷的实际判定区间为原判定区间减去水雷判定区间和蓝键resonance判定区间的交集，蓝键的resonance判定区间不变，echo区间为原echo区间减去水雷判定区间和原echo区间的交集」).** Where a MINE's window `M = [T_m ± MINE_WINDOW_MS]` meets the ±TIER2 window of a tap or STREAM head of the same line and lane, the mine loses the note's RESONANCE window `R = [T ± TIER1_MS]`, R stays whole, and the note's ECHO loses M; the note is LOST at the end of what is left (`GameEngine.judgeWindowMs(i)`). One press there either touches the mine or judges the note. TIDE notes are not affected.
  * **LANE MINE priority (owner 2026-10-14 13:52, 「如果说一个note和轨道水雷/水雷同时出现，那么note的resonance判定优先于轨道水雷和水雷」).** A tap or STREAM head of the same line and lane whose RESONANCE window `[T − TIER1_MS, T + TIER1_MS]` meets a LANE MINE's block `[T, end)` is judged first: the LANE MINE sleeps over that window (no contact from any pointer or key; a pointer still in its box or a key still down when it wakes after `T + TIER1_MS` is a contact, the one that judged the note included), and the note has no ECHO (judged only within ±TIER1, LOST at `T + TIER1_MS`). **RESONANCE guard (owner 2026-10-30, 「就是打出共鸣以后保护区间是150ms，这个区间内同一轨的红键失效」):** a RESONANCE at `t` on such a note also keeps every LANE MINE of its lane and line asleep until `t + RESONANCE_GUARD_MS` (150 ms); a pointer or key still there when it ends is a contact. A LOST gives no guard. (Until 2026-10-31 MINEs followed this rule too, with a ±66.67 ms danger span.)
  * Not touched by `T + MINE_WINDOW_MS` → it passes silently (fades out). Avoiding a mine does not add combo.
  * Mines are excluded from `totalNotes`, from the score denominator, from accuracy and from `judgedCount`. FULL COMBO = `maxCombo == totalNotes` **and no mine touched**; ALL RESONANCE = FULL COMBO and every note RESONANCE. **As built 2026-10-12:** `ScoreKeeper.isFullCombo()` = `totalNotes > 0 && maxCombo >= totalNotes && minesTouched == 0`, `isAllResonance()` = `isFullCombo() && isPure()`. A MINE or LANE MINE touched before the first note or after the last one resets only an empty or finished combo, so the combo alone would keep both badges; §14 says a touched mine removes both. (**Replaced:** "Full combo / all-resonance stay `maxCombo == totalNotes` based, so touching a mine mid-song loses FC naturally.")
  * Autoplay never touches mines.
* Candidate selection on touchDown (replaces §10's first bullet where they differ): candidates = unjudged lane notes (tap/hold heads) in the resolved lane (+ neighbour tolerance) **plus** unjudged universal notes, on every line whose zone contains the touch, with `|dt| ≤ TIER2_MS`; pick the earliest judgement time; tie → smallest `|dt|`; then lane notes before TIDE, own lane before neighbour, the closer line, and finally the lower line (only when both lines coincide and everything else is equal). **Replaced 2026-10-12** by joint judging (§20): "exact tie between a lane note and a universal note → the lane note (a second finger can take the universal note anywhere)". A tap that judges a lane note now also judges the TIDE notes of that exact beat on that line; a tap that judges no lane note falls back to the TIDE notes alone. **Since 2026-10-24** (Kelvin: a dense TIDE + DROP run in Confusion Deep, 1/8 beat apart, lost its DROPs whenever two fingers landed out of order, because the earlier pair's TIDE beat the tap's own DROP on "earliest" and the slip carried on pair after pair): when the input has a lane candidate on a line, that line's TIDE candidates skip every TIDE whose exact beat still has a pending tap / hold head on that line, since that TIDE waits for its lane note and is judged with it (§20). A TIDE with no lane note on its beat keeps the earliest-first rule; an input with no lane candidate, and Space, still take the earliest TIDE.
* Desktop key map by lane id: lower row −5..−1 = CapsLock, A, S, D, F and 1..5 = J, K, L, ;, ' ; upper row −5..−1 = Tab, Q, W, E, R and 1..5 = U, I, O, P, [ . Lane 0 (an inserted lane, §13.1, 2026-10-15) = G or H (lower), T or Y (upper); without a lane 0 they take TIDE notes only, like any key whose lane is absent. Lanes beyond ±5 have no default key.

* **Format v4 (owner 2026-10-19 14:55, binding):** v3 with the default lines at 1080 / 120. * `offsetMs` (v2, optional, default 0; added 2026-10-11 for the re-timed tutorial): audio time in ms of chart beat 0, so beats stay on clean values when the music starts late (the tutorial WAV's beat 0 is at 27 ms). Both are v2 only for `HeightEvents`; a v1 mine with a positive duration is also a LANE MINE (no shipped v1 chart has mines).
* **v1** (no `formatVersion`; every shipped song chart — the tutorial is v2) converts at load, exactly preserving today's visuals and judging:
  1. `lane` outside 0..19 → `lane % 20` (115 → 15, logged once).
  2. `line = lane ≥ 10 ? upper : lower`; `c = lane % 10`; new id = `c < 5 ? c − 5 : c − 4` (0 → −5, 4 → −1, 5 → 1, 9 → 5).
  3. Declared lanes: always all ten, ±1..±5, width 240, opacity 1 (today's layout is `bounds / 10` regardless of which lanes are used). Bounds and line events are copied unchanged, so the window −240..2160 keeps ±5 off screen and the 0..1920 squeeze brings them in, as today. **Since 2026-10-13** the window is read as global lane scale and camera frame (§13.1): −240..2160 is scale 1, camera 0, the squeeze is scale 0.8.
  4. Duplicate removal (§8) is gone since 2026-11-02 (Kelvin: 「现在我们要放开这个限制」): taps / holds sharing a line, lane id and judgement time all stay, and each press judges one of them (the earliest pending, file order on a tie), so a stack of n takes n fingers. Mines and universal notes were never removed (stacked ones are intentional, see §13.2; mines since 2026-10-22).
  * As built: a v1 chart without `leftBound/rightBound` gets −240 / 2160 (v2: 0 / 1920); until 2026-11-02 duplicate removal ran for v1 and v2 alike, keeping hold over tap (the longer hold between two holds, else the first). Since 2026-10-22 (Kelvin: 「地雷的限制不用那么多」) mines are never removed: stacked mines all stay (one contact touches each of them), and a mine on a tap's or hold's exact beat, line and lane stays and is played by note priority (§13.2).
* **Default approach (binding, GAMEPLAY rule in `elements/Note`; the editor and any converter must agree).** Outside every movement event a note sits at `HIDDEN_POSITION` 2000. **Since 2026-10-13 (owner, charter thread) authored motion is used exactly as written**, also right before the judgement: a note may show over beats 24–26 and be judged unseen at 29. So:
  * only a note with **no movement events at all** uses the **synthetic approach**: distance **1080 → 0, linear, over the 2 beats before its judgement** (`DEFAULT_SPAWN_DISTANCE`, `DEFAULT_APPROACH_BEATS`: the shipped charts' 540 units/beat; 972 / 486 in the 1080 frame of format v1 / v2), and `usesDefaultApproach()` is true; `Note.movementEvents()` and `ChartMapper.write` keep no events for it;
  * a note with movement events uses them unchanged; the position at the judgement (used to extrapolate a missed note's slide through the line) comes from the **last event that started** by then (its final value if it already ended), and is `HIDDEN_POSITION` when that event ended before `judgement − 1/32` (`APPROACH_PROBE_BEATS`) or none started: the note stays off screen after its judgement too;
  * **format v1 keeps the old rule** (shipped charts contain judged notes whose authored events never bring them on screen; before the default approach 28–29 notes per hard chart were invisible): the converter replaces the movement of a v1 note whose events do not cover `judgement − 1/32` (no events, events only after the judgement, zero-length, inverted or early-ending events) with the explicit event `Note.defaultApproachEvent(judgement)` (`Note.v1NeedsApproach` decides), so the look is unchanged and survives a save as v3;
  * **Exception: no approach (owner 2026-10-12 21:09, the original game's behaviour).** A note with **no movement events at all** whose authored `appearance` is at or after its judgement gets no synthetic approach. A tap, TIDE drop or mine is never drawn: it is a hidden judgement point cued by another note, such as the bouncing notes in marsh mally. A hold, TIDE STREAM or LANE MINE appears on its line just after its judgement and shrinks to its end (the "instant bar", e.g. marsh mally Abyss beats 107.5, 123.5 and 555.5). A missing `appearance`, or one before the judgement, still gets the default approach; the tutorial is written that way.

## 17. Afterimage trails "拖拽残影" (owner request 2026-10-11, binding; looks in DESIGN §17)
The owner asked: every note can drag a string of copies of itself behind it while it falls, fainter and fainter; the copies are only a show (never hit); the charter sets how dense they are and how long they last; every note type has it; the tutorial teaches it. Reference: a Phigros screenshot where sideways-moving notes leave copies that "fall vertically".

* **Chart key** (v2 notes, every type: `tap`, `hold`, `mine`, `universal`; optional; absent = no trail):
  ```json
  "trail": { "length": 0.5, "density": 16, "alpha": 0.6, "fade": 1.0, "mode": "path", "from": 30, "to": 32 }
  ```
  * `length` (beats, ≥ 0): how far back in time the trail reaches. 0 = no trail.
  * `density` (copies per beat, > 0): copies are `1/density` beats apart. Copy count `n = min(MAX_TRAIL_COPIES = 256, floor(length·density + 1e-4))` (32 until 2026-10-22, when Kelvin asked for the charter to set very many by hand); n = 0 → no trail.
  * `alpha` (0..1, default 0.6): opacity of the nearest copy relative to the note.
  * `fade` (default 1.0, clamped 0.05..20): copy k (k = 1 nearest … n farthest) has opacity `alpha · (1 − k/(n+1))^fade`, times the note's own opacity (`DisappearEvents`) at the copy's moment. Same power-curve idea as the chart events.
  * `mode`:
    * `"path"` (default): copy k is the note **exactly as it was** `k/density` beats ago: the lane x of that moment (LaneLayout and window evaluated at that beat), its distance from the line and the line's y at that beat, its angle, its size and (hold) its length. A note falling straight down leaves a straight column of copies behind it; a note in a lane that slides sideways leaves a slanted trail along its path; a rotating note leaves copies at its earlier angles.
    * `"level"`: copy k takes the note's **sideways position, lane width and angle** from `k/density` beats ago but keeps the note's **current** distance from the line, i.e. the copies fall straight down level with the note. That is the sideways smear of the owner's reference image (copies beside the note, not above it). A note that only falls straight down shows no level trail.
  * `from` / `to` (beats, optional): only copies whose moment lies in `[from, to]` are shown, so a charter can switch the trail on for part of the fall. `from > to` → swapped.
* **Visual only.** The engine never reads trails: copies are never judged, never touched, never counted, never block or consume input, never trigger FX or sounds. Mines' copies are not dangerous.
* **Lifetime of a copy** with moment `s = beat − k/density`:
  * drawn only when `s ≥ note.visibleFrom()` and `s ∈ [from, to]`, and the note's state at `s` is on screen (not `HIDDEN_POSITION`);
  * a note that was **hit** (any judgement but LOST) at beat `h`: `path` copies need `s < min(h, judgement)` — the trail drains into the line behind the vanished note; `level` copies disappear with the note;
  * a **missed** note (LOST, a mine that passed or was touched): copies keep following the note's miss slide and miss fade evaluated at `s`;
  * **hold**: copies sample head, body and tail at `s`, but never for `s ≥ judgement` (after that the head is pinned to the line and a copy would sit on the live hold);
  * TIDE (universal): the full-window bar is copied (window of that moment in `path`, current window offset sideways is meaningless so `level` uses the current window); the tide wash, the sync square and hit FX are never copied (**Replaced 2026-10-12:** "the tide sweep, sync outline/connectors", which no longer exist). As built: a TIDE drop's copy is the T4 look of its line (sky pearls, ground rolling wave, DESIGN §5.15, §17.1), and so is a TIDE STREAM head's since 2026-10-22 (DESIGN §24.54), mines' copies turn like their note, and a LANE MINE's copies are its head cap and column.
* **Model.** `elements/NoteTrail` (immutable value, pure Java): `length, density, alpha, fade, mode (PATH/LEVEL), from, to`, `copies()`, `spacingBeats()`, `alphaOf(int k)`, `NoteTrail.NONE`. `Note.trail()` never returns null. `ChartMapper` reads `trail` on v2 notes (key case-insensitive), sanitises (NaN/∞/negative length → 0, density ≤ 0 → NONE, alpha clamped 0..1, fade clamped, unknown mode → path, missing from/to → ±∞) and logs once per chart. v1 charts get no trails. Default-approach notes work the same (motion is a pure function of the beat).
* **Rendering** (gameplay owns it; `gameplay/TrailRenderer` or inside `NoteRenderer`):
  * copies of a line's notes draw **before (beneath) all live notes** of that line, farthest copy first, with the **same sprites** as the live note (NinePatch body, leading edge, rim; mine studs; tide diamonds, gone with the TIDE STREAM head bar on 2026-10-22), normal blend, no additive glow for copies;
  * past geometry: lane span and window at a past beat via a scratch `LaneLayout` (or a pure `LaneLayout.spanAt(index, beat, …)` helper), line y via the line's events at that beat; **no allocation per frame**; trails never change `LaneLayout`'s per-frame state used by input;
  * in 3D (7.216; 7.228, owner 2026-11-10 02:17 「残影要加上」): a copy of a key on a turned lane is drawn through that lane's frame at the copy's moment (`View3D.pastFrame` from the scratch layout), so a key moving with its lane leaves its copies where it was, and is not culled by the flat picture's edges (as the live key, 7.218); a key on a sea or a space key goes through its frame now;
  * budget: at most `MAX_TRAIL_QUADS` quads per frame (2,400 at particle quality High, 1,200 at Low and Off). Over budget, every trail is thinned uniformly (draw every 2nd, then 3rd … copy, alpha × 1.25 capped at 1) instead of dropping whole trails. Trails must not add a draw call (same atlas/batch as notes) and must keep gameplay at 60 fps in the tests with 40 trailed notes × 32 copies on screen, and × 256 (the most). The budget stride never goes past the longest trail's copy count (each trail keeps one copy there).
* **Docs/tests.** `docs/CHART_FORMAT.md` documents the key with examples of both modes; pure tests for parsing/sanitising/`alphaOf`/lifetime; a v2 test chart with trails (straight fall, lane slide in both modes, rotating note, hold, mine, TIDE, from/to window); screenshots.
* **Tutorial.** A short afterimage lesson (DESIGN §17.3).
* **Segments (owner 2026-10-14: 「一段时间加残影另一段时间不加都做不到」).** `trail` may also be an array of trail objects; each is a segment with its own `from` / `to` and look, nothing shows between segments, overlapping segments both draw. `Note.trails()` lists them (`Note.trail()` stays the first); `TrailRenderer` gives every segment its own slot (planned, budgeted and drawn like a trail of its own); `TrailPlan` and `TrailGeometry.place` have overloads taking the segment. One segment is written as an object, more as an array.
* **Glitch (owner 2026-10-14, approved preview).** A per-note `glitch` (object or array of segments: `from`, `to` or `duration`, `intensity`, `intensityEnd`, `exponent`, `rate`, `split`, `slice`, `flicker`; CHART_FORMAT_v4 §6.9) cuts the note into sideways-moving strips, adds a red and a blue copy and flickers it, the pattern changing `rate` times per beat. Visual only, like trails. Model `elements/NoteGlitch` (`intensityAt`, `step`, `activeAt`: the segment that started last wins); `Note.glitches()`. Rendering: `NoteRenderer` points its batch at a `gameplay/GlitchCapture` (a recording `Batch`) while a glitching note draws, then replays the recorded quads into the atlas batch (strips clipped per quad, copies under the note); the note's glows (sync frame, glow) replay in the additive pass through the same capture with the note's strips (no colour split); trails and FX are not glitched. ## 18. Scoring v2 (owner's formula 2026-10-11, revised by the owner 2026-10-14, binding; overrides the score parts of §5, §13.2/§13.4 and DESIGN §11/§12 where they differ; looks in DESIGN §18)
* **Formula (2026-10-14).** With `t` = judged notes in the chart (`totalNotes`: taps, hold heads, every TIDE member; mines excluded), `r` = RESONANCE count, `e` = ECHO count, `m_r` = longest run of consecutive RESONANCE judgements (**resonance chain**), `r_p` = PERFECT count (RESONANCE with `|Δt| ≤ 1000/30 ms ≈ 33.33 ms`):
  ```
  score = 100,000,000 · (r + 0.55·e) / t + 10,000 · m_r / t + r_p
  ```
  The chain is a small bonus next to accuracy (at most 10,000), not a 10 % share of the score as in the 2026-10-11 formula `100,000,000 · (0.1 · m_r/t + 0.9 · (r + 0.55·e)/t) + r_p`. Exact integer form (no float drift, rounded down once): `base = floor((100,000,000 · (100·r + 55·e) + 1,000,000 · m_r) / (100·t))` in `long`, `score = base + r_p`. `t = 0` → 0. Maximum = `100,010,000 + t` (every note PERFECT). `base == 100,010,000` exactly when every note is RESONANCE. For the same play the new score is never lower than the old one, so best scores saved before 2026-10-14 need no conversion; replays overwrite them.
* **Two different streaks.**
  * **Combo** (shown in the HUD, used for FULL COMBO): consecutive RESONANCE **or** ECHO; reset by LOST, by a touched mine and by every LANE MINE contact. FULL COMBO = `maxCombo == x` and no mine touched (§13.2).
  * **Resonance chain** `m_r` (used in the score): consecutive RESONANCE only; reset by ECHO and LOST. A touched mine does **not** reset the chain. ~~Touching a mine never changes the score~~ (owner rule: "碰到不扣分但是断连击"); **since 2026-11-01** every touched mine costs 10,000, once per mine however often it is touched (`Judgement.MINE_PENALTY`, `Judgement.minePenalty`, `ScoreKeeper.minePenalty()`; Kelvin 20:14: 「水雷改为打中一个加10000分吧不然水雷少的谱面就很难了」, 15:48: 「轨道水雷和潮水水雷如果碰到多次也只加一次」; from 15:47 to 20:14 all mines together cost 1,000,000), so `score = base + PERFECT − mine penalty`, which can go below 0 (it then reads positive; records keep at least 0).
* **Constants** in `play.Judgement` (aliased by `Params`): `PERFECT_MS = 1000f/30f`, `WEIGHT_TIER2 = 0.55f` (ECHO), `MAX_SCORE = 100_000_000` (full accuracy term; the cap of grades, rating and EXP), `CHAIN_SCORE = 10_000` (full chain term), `MAX_BASE_SCORE = 100_010_000`, `static int baseScore(chain, resonance, echo, totalNotes)`, `static int chainScore(chain, totalNotes)` (the chain term alone, for the result breakdown), `static int maxScore(int totalNotes)` = `MAX_BASE_SCORE + totalNotes`, `static boolean isPerfect(float absDeltaMs)`. The three judgement grades stay RESONANCE / ECHO / LOST; PERFECT is a sub-count of RESONANCE, not a fourth grade (no new enum constant).
* **`ScoreKeeper`** (pure, allocation-free): `record(j, deltaMs)` also updates `perfect` (RESONANCE with `|Δt| ≤ PERFECT_MS`), `chain`/`maxChain`; `mineTouched()` resets combo only; `breakCombo()` resets both; `score()` = `baseScore() + perfectCount()`; `baseScore()`; `maxScore()`; `chain()`, `maxChain()`, `perfectCount()`; `earlyResonance()` / `lateResonance()` = RESONANCE hits that are not PERFECT with `Δt < 0` / `Δt > 0` (so PERFECT + early + late = r; `early()` / `late()` stay the ECHO-range hits beyond ±TIER1); `accuracy()` = (r + 0.55·e) / judged (ECHO weight 0.55 everywhere). * **`PlayResult`** gains `perfect`, `maxChain`, `baseScore`, `earlyResonance`, `lateResonance` (`Builder.resonanceEarlyLate`); `score` is clamped to `0 .. MAX_BASE_SCORE + totalNotes`, `baseScore` to `0 .. MAX_BASE_SCORE`. `RecordOutcome` unchanged in shape.
* **Grades** (DESIGN §18.3): `Rating.gradeOf(int score, boolean allResonance)`: PURE only when `allResonance`; otherwise by thresholds on `min(score, 99,999,999)`. `gradeOf(int score)` (records without the flag) treats `score ≥ 100,000,000` as PURE.

* Kelvin: 「定轨状态支持小数轨道，然后加一个无轨时间和有轨时间。有轨时间默认6轨。无轨时间内横向拖动精确到5px。」 A tap, STREAM or mine (LANE MINE too) has a lane that may be a decimal (`Note.lanePos()`; the floor is `laneId()`), or no lane but an `x` / `xEvents` like a DRAG (`Note.laneless()`, the constructor's `byX`; a lane wins when both are written). `Chart` resolves a whole lane it has to that lane; a decimal, or lane 0 when the chart has no lane 0 (the centre line, formerly dropped), is `between()` (`laneIndex()` −1); a whole lane it lacks is still an error (the loader auto-adds it first). `free()` = laneless or between. ## 28. The view (owner 2026-11-07 06:35–06:46 and 15:34, binding; format in CHART_FORMAT §5.6)
* `Chart.viewYaw/viewPitch/viewFov/viewDist`, read and written by `ChartFormatV5` (top-level `view`), also read by `LegacyChartFormat` (events in the old shape: the editor's working text), evaluated with `Events.calculateValue` like every other motion channel (Kelvin 2026-11-07 16:04 「3Dcamera这些也都是运动类事件」, 7.200; 7.198–7.199 used smoothstep and held the last value): the default between events, so a held turn is written as a flat event.
* Column reach (Kelvin 15:58–15:59, 7.200): `Chart.upperExtendAt/lowerExtendAt` (`lines.upperExtend` / `lowerExtend` + events, default `Chart.DEFAULT_EXTEND` 820, never below 0) is how far a column reaches past the sky / ground line. `View3D.columnStops` cuts the column into (y, opacity) stops: solid between the lines and up to `COLUMN_FADE` (700) short of each end, then a smoothstep fade in `FADE_SEGMENTS` pieces (all of a reach under 700 fades). * `View3D.update` places a `PerspectiveCamera` over the screen's flat camera. `dist` (reference units × ky; default `autoDist(fov)` = 600 / tan(fov / 2), the distance at which the front plane fills the lens; default fov `DEFAULT_FOV` 11) is to the columns' front plane when facing straight; yaw and pitch circle the screen centre at half the column depth, at `dist` + half the depth. Finite-lane charts (`laneCount`) are always drawn in 3D at the full depth `DEPTH` (240) × ky: at the default the front plane is exactly the flat picture and the depth shows as on the 3D page's default view (back faces 0.96 the size of the front). Unlimited charts: at the default (no turn, default distance) it returns false and the screen draws exactly as before; off it, depth = `DEPTH` × ky × min(1, turned angle / 15°).
* When it returns true, `GameplayScreen.render` ends the batch, draws `View3D.drawBack` (columns, mother planes, faded in with the lanes' intro) and `drawBoxes` (TIDE sheets and the key boxes `NoteRenderer.collectBoxes` records from the same geometry as the flat draw; since 7.206 also every MINE and LANE MINE cap and column, in `NoteRenderer.MINE_BOX` red, and a key or MINE whose front shows the sync frame records its frame colour: `drawFrames` then adds a thin glowing line along the four edges of its back and the four along its depth, strips turned to the camera, Kelvin 19:37), then the field blocks through `view.combined()`; the HUD, banner scrim, judgement words and touch rings stay on the flat camera. The hit effects are spheres round the middle of the keys' depth (Kelvin 17:04, 7.204): `HitFx.setView(view)` (`View3D` implements `HitFx.Projection`) and `HitFx.draw` on the flat camera; each ring, flash, held light and drop is drawn facing the screen where `project(x, y, dz)` puts its point (`dz` nearer than the middle, times the depth share), at the size one unit shows at there, so it stays round however the camera turns; the drops also fly in depth (their own random numbers, at most as fast as sideways), and a LOST mark starts where its point shows. Since 7.205 (Kelvin 17:52, the design thread's 3D page v17) a ring in 3D is a lit sphere: `WaterRings` draws the `Draw` region `shell` (the α of both faces of a clear sphere: rim (1 − |n·v|)^2.2 × 0.95 plus a faint fill) at the shaded base brightness, `shell_lit` (the same times (1 + x) / 2) turned towards the light for the n·L shading, and a highlight spot (key colour and white, squeezed along the light) where the light's eye-space direction meets the sphere; the light (−0.45, 0.75, 0.5) is fixed in the world and `Projection.direction` turns it into the camera's frame. Flashes, held lights and drops get a small white glint towards the light (`Splash.glint`). `HitFx.clear` goes back to flat drawing. All 3D geometry lies at z ≤ 0 behind the flat picture and the camera stays in front of it, so drawing the flat picture last is a correct order without a depth buffer.
* Touch: `GameplayScreen.toField` → `View3D.toField`. Facing straight (yaw and pitch 0): the press's point on the front plane (the identity at the default, so judging is exactly the flat one, a gap press going to the nearer lane). * `View3D.drawSeas` (after `drawBack`, before `drawBoxes`): each sea shown is one sheet over [x0, x1] × [z0, z1] across the gaps, filled `Theme.SEA` × `SEA_A` with its front edge in `SEA_EDGE`, heaving `heave(x, d, t)` = 7·sin(2πx/280 − 2t) + 7·sin(2πd/260 − 1.4t + 0.004x) on a grid of at most 96 × 32, t the song seconds (`NoteShapes.songSeconds`, so stills repeat). `drawBoxes` heaves each TIDE sheet piece the same way on its own x and depth. The flat picture (unlimited lanes, untilted): `FieldRenderer.drawSeas`, a band of ±`SEA_HALF` around the surface with a thin edge, heaving at the front edge's depth.
* Known limits: a sea's part in front of the front plane (z0 < 0) is drawn before the flat picture, so keys and lines cover it; on an unlimited chart turned by zoom alone (no depth) only its front edge shows.
